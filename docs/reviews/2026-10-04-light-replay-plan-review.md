# Light Replay 最新方案评审：先让一个目标点的答案可信，再完成照片回放

日期：2026-10-04（Australia/Melbourne）  
评审：Codex  
对象：[Light Replay 方案与执行清单](../proposals/2026-10-03-light-replay-plan.md)，同时核对其前置[天空分割方案](../proposals/2026-10-03-sky-segmentation-plan.md)。  
基线：`feat/inspect-screen`，`3151c212667d7297f99011c519b475c0b09843ba`；开始审阅时工作区干净【验】。  
范围：文档、相关源码、定向算法检查与 Apple 官方资料。只新增本评审，不改产品代码、不修改已接受的 ADR、不提交或推送。

标注：数字后的【验】指本轮源码核对或合成计算；【引】指既有文档记录、未在本轮复验；【估】指建议或假设。编号、日期、版本、字段名和代码字面量是定位信息，不代表测量结果。

## 结论

**支持 Light Replay 成为下一条主线，但不建议原样批准当前执行清单。**

方案抓住了真正有价值的体验：回家打开自己拍的照片，查某个日期、某个时刻，这个位置有没有可能得到直射；再看哪些部分可信、哪些仍未知。照片提供记忆，时间轴提出问题，可见域与方向证据给出答案。这比孤立地展示一张太阳轨迹图更符合 Property Replay 的产品目标。

我赞成保持现有质量门槛，也赞成 Save 后分析、保留累积网格与少量关键帧的路线。需要修正的是：方案把几个尚未成立的测量和持久化假设，当成了可以直接排期的工程步骤。

**建议把下一阶段的交付定义成：一个目标点、一个日期、一份真实网格，从采集到回放可闭环，失败与未知也可解释。** 合成数据可以先验证回放交互；真实分割、方向采集和现场真值应尽早进入关键路径。原定约四周【引：方案 §6】只能作为初步预算，不能作为验收或发布承诺。

## 执行前需要解决的问题

以下 P1 表示应在相应实现进入主链前解决的计划缺口；并不表示当前已经上线了同样的缺陷。P2 表示首版范围与验收需要澄清。

### R01 · P1：帧卷必须保存可计算的同步输入，不能只有 JPEG

**位置：方案 §4.1、§4.2，原 PR 1–2。**

方案明确保存降采样 JPEG，却随后依赖近距离深度做负种子和目标点重投影。当前 `FrameSample` 只有 `hasSceneDepth` 布尔值；`SceneRecordBuilder` 写出的 `depth_ref` 与 `depth_confidence_ref` 都是 null【验】。保存图片并不会自动补齐这些输入。

同样，Hero 与分割图像都被缩小，不能继续直接使用原始分辨率的内参。`PinholeCamera.pixel(of:)` 使用像素单位的焦距和主点，不会自行适配缩放。合成例：图片宽从 1920 缩到 960，主点从 960 变成 480【验：缩放计算】，否则即使太阳方向正确，也会投错像素。

**建议补一个最小帧卷契约：**每个用于分析的帧包含稳定 `frame_id`、同帧单调时间戳、camera transform、原始图像尺寸与内参、编码图像尺寸、裁剪/缩放/旋转变换，以及可用的深度、深度置信度、深度尺寸与配准约定。抽帧必须把该帧的姿态一并保留，不能事后随便取临近的姿态日志拼接。无深度设备继续遵循既有降级规则，明确其几何限制。

图像坐标到掩膜坐标、AR 原生方向到界面方向也应写成同一条变换链。Apple 的 Vision 点坐标原点在左下角，不能直接当作图像左上角像素坐标使用。[Apple：What’s new in image understanding](https://developer.apple.com/videos/play/wwdc2026/237/)

**验收：**同一合成场景在不同分辨率、横竖屏与不同掩膜尺寸下得到一致方向；近窗框的已知深度能重投影到同一个 TargetPoint；缺少深度或元数据的输入明确降级。只有这些成立，PR 1 才算为离线分析准备好了输入。

### R02 · P1：几何种子是待验证的猜测，不能直接代表天空

**位置：方案 §4.2 第一步、原 PR 3；天空分割方案 §2。**

“高度角大于 30°【引：方案】且在太阳走廊内”只说明方向，不能说明该像素是天空。檐下、室内天花板、高楼、树冠都可能满足这个条件。错误正种子可能稳定地把遮挡分成“天空”；连续多帧投票仍可能重复同一个错误。

还有一个具体边界：使用仓库 Python 参考实现，以城市级合成坐标计算墨尔本冬至，太阳最高视高度约为 28.783°【验】。如果种子约束取当天太阳路径，本身就可能没有超过上述门槛的点；若采用外扩或多日期走廊，是否有候选取决于走廊定义，仍不能据此证明候选是天空。

Apple 将 `GenerateIterativeSegmentationRequest` 定义为由种子引导的对象分割，官方示例没有承诺它自动识别“天空”语义，也没有证明输出就是校准后的逐像素天空概率。[Apple：What’s new in image understanding](https://developer.apple.com/videos/play/wwdc2026/237/)

**建议：**把“种子是否有效、掩膜是什么含义、置信度来自哪里”列为 W1 的首要实验。没有可靠正种子时返回 Unknown 或进入已接受的人工标注降级。玻璃启发式同样先作为待评估检测器：没有触发不等于证明没有反射。

保留原有 IoU ≥ 0.90 的候选线【引：`07` §5】，另外按太阳走廊检查“遮挡误报天空”、无天空帧、错误种子、玻璃反射和重复帧；这些是补充诊断，不自行替换或放宽预注册线。三票【引：方案】应说明是不同有效帧的计数还是权重和，避免把相关帧当作独立置信证据。

**验收：**天花板占满画面时不能产生可接受的天空证据；无种子时不崩溃且明确降级；整体 IoU 好看但关键走廊错误的样本必须被单独报告。

### R03 · P1：敏感时段长度不是“±N 分钟”的误差界限

**位置：方案 §3.2、§4.4、§9。**

`SunBands` 实际按直射比例达到 0.95 判稳定直射、不超过 0.05 判稳定遮挡【验】，不是方案所写的“全部抽样都直射/都遮挡”。单次日盘混合状态也会参与计算；未知/玻璃还会产生 Unknown。`DayBands` 提供状态段与累计分钟，没有提供事件边界的置信区间【验】。

敏感段可能来自日盘跨过遮挡边缘、方向扰动、边界抖动，且可能不对称、分成多段。把这段长度直接写成“±N 分钟”，既没有定义中心事件，也没有给出置信水平。方案用“观测误差 ≤ 敏感段宽度”做验收，会允许通过放宽敏感范围来显得正确。

**建议首版直接展示稳定直射区间、敏感区间和资料不足区间，删除未经定义的 ± 分钟。** 需要误差区间时，再设计各次抽样中同一进出事件的匹配、分位数与无事件情况，补 schema 与测试。不能只改文案模板。

产品示例可改成：“这个位置：稳定直射时段见色带；斜纹时段受方向或遮挡边界影响；空心时段资料不足。”实际时刻全部由工具填入。Compare 有未知时不能把稳定直射累计直接命名为“全天日照总时长”；可写“已确认直射”并标资料不完整。

**验收：**R0 不出小时数；多段直射不被合并成一个连续区间；Unknown 不成为确定时长；中英文本从同一份结构化结果取数，并按项目要求做 Assist 数字回归。

### R04 · P1：可以要求确认后才出 R1，但不能把“一次点选”当成完整方向证据

**位置：方案 §2、§3.1、§3.2、§5、§8；原 PR 5。**

方案前半仍展示“只有罗盘、黄灯、大约小时数”，后半才说明罗盘精度不足必须阻断。当前 ADR-0018 和实现支持后半的判断。使用同向的合成候选运行现有 Python resolver，结果如下；σ 是人为构造的测试输入，不是本轮现场测量：

| 合成候选 | 输出【验】 | 对方案的含义 |
|---|---|---|
| magnetic σ=13° | blocked，未佐证 | 不能显示方案里的罗盘黄灯 R1 示例 |
| magnetic σ=13° + solar σ=2° | warn，融合 σ≈1.977°，未佐证 | 太阳确认可以使方向不阻断，但与罗盘一致不叫佐证 |
| solar σ=2° + map σ=4° | pass，融合 σ≈1.789°，有佐证 | 同时满足一致性与分辨能力，才有这里的绿灯 |

更关键的是，`05-north-resolver.md` §2–3 明确：窗光斑校准需要已知窗几何、窗边与光斑边对应、残差检查。只点一下地上的光斑不足以唯一确定太阳方向。墙面对齐也需要实际竖直平面、可用建筑轮廓、用户选中正确边；不能把它视为阴天时总能完成的兜底。太阳圆面选点是另一条采集路径，需要独立的证据与误差处理。

**建议：**保留路线 A 的质量原则，先挑一条可测的太阳圆面确认路径做真机闭环；窗光斑与地图对齐分别列出依赖后再承诺工期。扫描结束时尽早提示方向证据不足，但始终允许“保存为参考”；无法确认时保留 R0，不阻止保存。回家后的按钮应说明需要补采，不能暗示离开现场后还能凭空确认原会话的方向。

**验收：**无太阳、无轮廓、错误选边、确认失败都能保留扫描；无效候选不进入融合；只有方向灯改善不能直接升级整条记录，还要满足其他门槛。确认耗时必须计入 OneTake 的采集时长，不能单独从指标里剔除。

### R05 · P1：Caches 与后台调度无法兑现当前“随时重试、不丢扫描”的承诺

**位置：方案 §4.1–4.2、原 PR 4。**

现场帧离开现场后无法重新获取。若唯一输入只在 Caches，系统清理后剩下的 R0 JSON 不能重新分割。“记录还在”和“扫描仍可完成分析”是不同的保证。Apple 明确说明 Caches 可能被系统删除，应只放能重建或重新下载的数据。[Apple：File System Basics](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/FileSystemProgrammingGuide/FileSystemOverview/FileSystemOverview.html)

`BGProcessingTask` 也不是 App 退后台时对前台 Task 的无缝接力。后台执行由系统安排，可能被延迟或中断。可评估更贴近用户主动发起长任务的 `BGContinuedProcessingTask`，但同样要处理排队、取消与过期，不能把换 API 当作保证完成。[Apple：Finish tasks in the background](https://developer.apple.com/videos/play/wwdc2025/227/)

**建议：**分析完成前，把不可重建的帧卷当作本地待处理输入，采用持久目录、任务清单与明确清理期限；不放进共享或云同步载荷，备份策略显式定义。帧卷与任务清单落稳后才报告“已保存，可分析”。成功提交结果或用户明确放弃后再删原始帧卷。沿用现有 PendingCapture 的“先保住输入、再关联数据库”的思路。

最小状态应能区分：等待分析、分析中、等待资源、可重试失败、输入已缺失、分析完成但仅 R0、R1 可用。界面中的“分析完成”不等于“获得有效测量”。

**验收：**在输入落盘、分析中途、结果提交、清理输入各阶段中断并重启；模拟缺盘、缺模型、任务过期；删除观察后任务不能把它重新写回来。重试必须有输入可用性检查，输入丢失不能反复显示一个永远无法成功的重试按钮。

### R06 · P1：schema、资产与结果提交契约必须前置，不能放在倒数的文档 PR

**位置：方案 §4.2、原 PR 1、4、8。**

当前校验器仅接受 schema `0.1.0`【验】；R0 的 `analysis` 必须为空，R1 需要五盏灯都没有 blocked【验】，不只是方案等级表中的“三盏灯”。反射证据、网格与掩膜载荷、Hero 元数据如何写入、同步与校验，都会影响前面的实现。等 PR 8 才定 schema 会制造返工，甚至使已算好的结果无法合法落库。

“按 scene_id 幂等，重跑覆盖”也不充分。方向修正后旧任务可能晚到；算法更新后相同 scene_id 不是相同输入。用户的笔记、房间标签与删除操作也不能被旧结果覆盖。

**建议在首个数据写入 PR 前确定：**

- `scene_id` 是记录身份；分析另有 input hash、算法版本与结果 revision。哈希应覆盖网格/置信度、方向、地点与时区、查询、影响结果的选项。重复请求不重复应用，旧 revision 不覆盖新结果。
- 结果提交前验证五盏灯、guard 与全部引用；先准备完整资产，再发布一个可读取的结果版本。图库、Light 行、Compare 都从这份结果派生。
- 明确网格、关键帧掩膜、Hero 分别如何进入现有 SwiftData/iCloud 存储；另一台设备缺资产时显示等待下载/资料缺失，不能把本机文件路径当作同步后的资产。
- 保留旧 R0 的读取与校验；如果升级 schema，同时更新 Swift 与 Python 校验器、兼容 fixture 和导出载荷，不能只补一段文档。
- 区分“从已存网格重新算日照”与“从所有原帧重新分割/累积”。按 ADR-0019 删除多数帧后，后者不能完整重放；少量关键帧只支持抽查与排错，不应承诺完整重建。

**验收：**旧版记录可读；资源缺失不能显示为完整 R1；改北向后旧任务结果被拒绝；重复执行不改用户笔记；iPhone 计算后的记录在 iPad 读到的状态与资产一致。跨设备同日 scene_id 冲突是 HANDOFF 已知未结项，扩展任务身份时应一并明确处理，不能只依赖显示编号。

### R07 · P1：单点延时是首个闭环，不是整个测量链的最终验收

**位置：方案原 PR 9、§8；对照 `07` §3–6、`08` §5。**

方案只安排自家一个点、一天延时【引】，适合作为集成 smoke test。它无法替代既有 W3 的独立 holdout、室内外及玻璃/树冠/低太阳场景；也无法证明冬夏回放的现场准确度。

已有候选线是 accepted 场景中位误差不超过 10 分钟、P90 不超过 20 分钟，holdout false-valid 为零【引：`07` §5】。不得用“误差不超过敏感段宽度”静默替换。W1 的标注帧是分割路径筛选，不能既用于调参又作为最终证明。

**建议把验收拆开：**合成闭环证明实现遵循契约；自家现场证明真实输入能走通；冻结版本后的独立 holdout 才决定 GO / CONDITIONAL / NARROW。消费者范围与限制沿用路线图的汇合门。本轮不重开既有 TestFlight 时机决定，只澄清“回放做好”的验收含义。

**验收：**报告必须关联采集编号与延时事件编号，保留失败、放弃、未知和人工救场，不只统计成功点；通过线在测之前登记，不在看见结果后更改。

### R08 · P2：首版界面可以更聚焦，避免让视觉承诺超过测量能力

**位置：方案 §3，原 PR 6–7。**

建议保留 Hero 照片、日期、时间轴、当天色带和一句状态作为主屏；把天幕作为“为什么”解释入口。第一版先从房产的 Light 卡片进入，真实闭环通过后再加照片流与 Compare 入口。完整全年热力图不必成为首个可用回放的前置条件；这是实现分批建议，不是取消蓝图范围。

需要同时纠正这些契约：

- R1 只能回答这个 TargetPoint 的直射，不代表整张照片、整个房间或亮度。太阳方向标记可以画；“把遮挡它的那片画面描边”需要与 Hero 对应的像素证据，方向网格与 `blocked_west` 归因不能直接给出物体轮廓，首版建议先不承诺。
- 删除“一屏放下，不滚动也完整”的硬条件。最大辅助字号与横屏下允许滚动或自适应布局，以完整可读为准。日期选择器要有可见入口，不能只能长按。
- 日期行、预计算查询与实际查询要一致。现有代码以固定日期近似冬夏代表日【验：`engine/lightreplay/bands.py`】，若沿用就明确是代表日；不要暗示已经计算逐年的精确节气瞬间。时间始终用场景时区，并显示年份。
- 每个查询都要说明覆盖与未知；只扫冬季走廊，不代表夏季也有足够信息。北向修正后，要重新计算对应查询的覆盖，不能沿用旧百分比。
- R0 的“整条空心色带”与“不画任何色带”在原文冲突。建议区分参考太阳路径与测量结果区：R0 可以看参考路径，结果区显示原因，不画会被误读为已计算时间分布的色带。
- 方向证据不足、玻璃不确定、分析失败和资产未到本机，给不同解释。算法版本等技术信息放可展开证据区，默认先告诉用户结果适用哪里、缺什么。

**验收：**最大字号、横屏、深浅色、中英文、VoiceOver 都能完成选日期与调整时间；状态不能只靠颜色；所选时刻、当天累计与证据详情始终来自相同查询与结果版本。照片之外的方向标记不能被误读为照片里出现了实际光斑。
