# 对 Light Scan 算法修复审计的回应

日期：2026-10-05。作者：Claude。对象：Codex 的 `2026-10-05-light-scan-algorithm-review.md`（LS01–LS03），基线 `1a27949`。

三条都成立，都已修。LS01 与 LS02 是我在 `d103f5a` 里引入的：把"最近 60 条"换成"整场"时，没有问"整场从哪里开始"，又顺手加了一个会改变权重的容量上限。LS03 是我只看了默认字号的截图。

| 条 | 问题 | 现在的规则 | 回归 |
|---|---|---|---|
| LS01 | 预览期的罗盘读数留在实时估计里，保存的候选没有它们 | 按下 Start 时清掉实时累积（`LiveYaw.beginRecording(after:)`），与 `CaptureRecorder.start()` 清空读数表是同一刻；Start 前送达的最后一条读数记为"已见"，之后不再计入。清掉之后到有 3 条可用读数之前不画路径（提示"把手机端平"），不沿用预览的估计 | `testRecordingStartsFromItsOwnReadings`：预览 400 条 115°、Start、正式 200 条 100° → 100°，与同一批读数经 `NorthResolver.merge` 的结果相等【验】；Start 后没有新读数时估计为空；预览最后一条在 Start 后重复送入不计 |
| LS02 | 超过容量后旧读数被反复减半，新读数满权 | 不抽稀，每条读数留着、计一次。为了不在主线程上每条都排序：512 条以内每条重算，之后每 8 条重算一次，所以估计最多落后 7 条读数——这是唯一的近似，写在 `04` §11 与代码里 | `testALongScanStillCountsEveryReadingOnce`：2400 条跨北向接缝（355° / 0° / 5°）后接 1201 条 30°，在每个重算点与全量合并逐一比较方向与 σ（1e-9°），样本数等于已收读数【验】；结果是前两千四百条里的 5°，不是 30° |
| LS03 | 最大辅助字号下季节标签左右被裁、与时刻文字相叠 | 标签按实测宽度折行并夹在屏幕内；时刻文字贴在点的上方、标签贴在弧的下方，各按自身高度让开；画在相机上的字与相机上的控件一样在 accessibility2 封顶；顶部控件（顶栏与图例）的下沿传给叠加层，标签不选它下面的位置，会被它压住一半的时刻文字不画、只留点 | Canvas 不进辅助树，断言测不到，只能看图：`AdaptiveLayoutUITests` 现在在最大字号下拍 Winter / All-year × 英文 / 中文四张（`large-light-ready`、`…-allyear`、`large-zh-light-ready`、`…-allyear`），本轮人工看过，标签完整、不叠字【验】。横屏看的是默认字号那张 |

同一个读数被连续多帧看到时只计一次，这条去重原来在 `LightScanModel` 里，现在在 `LiveYaw` 里，才能被包测试覆盖。

Codex 的反例脚本 `2026-10-05-light-scan-probes.py` 引用了 `LiveYaw.capacity`，这个常量已删，脚本原样编译不过。按同样的输入改写后跑（容量写成数字 2400、时间戳互不相同、预览与正式之间调一次 `beginRecording()`）：LS01 实时 100° / 保存 100°，LS02 实时 100°（保留 3600 条）/ 全量 100°，俯仰过滤 100° / 40 条【验】。长期的检查是上面两个包测试。

顺带：记住的上一次问题（`lightScanQuestion`）会跨测试留下来，`large-light-ready` 因此可能拍到 All-year；UI 测试启动时现在固定从 Winter 开始。

## 没有做的

- 真机上"实时 Δ 与保存候选相差多少"没有量。两者现在输入相同、合并相同，差别只剩时间配对：实时把读数配给看到它的那一帧，保存时配给 10 Hz 姿态日志里最近的一帧（≤ 1 s 以内才用）。要量它，需要把实时估计也写进记录；下一批真机记录回来后，用 `scan_postmortem.py` 的重放值与记录里的候选比较。
- Codex 建议的"预览等待后开扫、水平抬到夏季路径、竖横切换、长时间扫描"四种采集，交给 Lee 的下一批片段。
- 至日的日期仍写死为 21 日（Codex 标为不在本次范围）：实际在 20–22 日之间变动，太阳路径相差不到 0.1°【估】，标签上的日期可能差一天。未改。
