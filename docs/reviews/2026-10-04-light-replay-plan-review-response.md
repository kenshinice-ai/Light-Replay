## 结论

八条全部接受，其中 R01–R07 我逐条回到代码或 SDK 核对过，评审说的都成立。v1 的问题是一类：把没验证过的测量假设当成了能排期的工程步骤，其中两处（罗盘黄灯、±N 分钟）还和我自己写的代码、ADR 对不上。v2 按评审的方向重排：契约与实验在前，界面在后，验收分三层。

有七处我在评审之上加了判断或改了做法，列在第 2 节。

## 2. 在评审之上的七处

1. **分割请求的接口比评审假设的多**【验：iOS 27 / macOS 27 SDK 的 Vision 接口】。`GenerateIterativeSegmentationRequest` 有 `addIncludedPoint` / `addExcludedPoint`，结果类型是可空的 `PixelBufferObservation?`，有三档质量，**macOS 上也有**。所以：排除点可以用 LiDAR 近物；"没分出来"有接口上的表达；评估可以在 Mac 上批量跑，不必每次上真机。它仍然是"按种子分割对象"，不认识"天空"——评审的核心判断不变。
2. **评估集要用 App 拍，不是用相机拍**。种子靠重力、深度、内参；普通照片没有。所以真正的分割评估排在 B（帧卷）之后；A 阶段只做一个不需要元数据的冒烟。这改了我上一轮对 Lee 说的"有片子了说一声"。
3. **太阳圆面是最好的第一条方向路径，因为它自带残差检查**：亮斑的高度角（重力给）必须等于算出的太阳高度角，不依赖北向。评审要求"先挑一条可测的"，这是选它的理由。另外方向确认与站位无关，可以走到看得见太阳的地方再对——代价是走动带来的偏航漂移，要量。
4. **第一版不做后台调度**。评审建议评估 `BGContinuedProcessingTask`；我认为 20 秒量级的任务用"前台跑 + 退后台的短暂宽限 + 下次启动续"就够，少一套会延迟、会过期的机制。以后任务变长再评估。
5. **资产内联进记录，Hero 复用照片列**。评审要求明确资产怎么进 SwiftData / iCloud；内联后一行一份记录、没有本机路径、不新增 CloudKit 字段（Production schema 10-03 刚部署）。代价是记录 JSON 大几十到一两百 KB【估】。
6. **镜头与水平两盏灯是 R1 的硬前置**。评审指出 R1 要五盏；落到工作上就是这两盏要有真检测器（SDK 里 `DetectLensSmudgeRequest`、`DetectHorizonRequest` 都在【验】）和可重算的证据。v1 完全漏了。
7. **TestFlight 分内测与外测**。评审不重开时机的决定；我建议把"replay 做好"落成两步，见下。
