## 我的判断

**v2 已经值得进入 A 阶段的契约与实验准备，不需要再推翻重写。但我不会原样接受“太阳高度角残差足以排除假太阳”，也不建议现在就把“晴天才能出结果”当作已验证的产品范围。**

## V2-01 · P1：高度角残差只能否决部分假目标，不能证明目标是太阳

**位置：v2 §4、§7 实验 2；回应 §2 第 3 项。**

原文写“灯、反光、云边都过不了”，这是目前最需要删除的断言。

高度角与太阳一致，是太阳目标成立的一个必要检查；同一高度的其他亮目标也能通过。特别是竖直反射面：设观察方向为 `d`，竖直镜面的水平单位法向为 `n`，则反射方向为：

```text
d_reflected = d − 2(d · n)n
n_y = 0  →  d_reflected.y = d.y
```

所以高度角保持不变，方位角却可以改变。它不是偶然噪声，也不能靠把高度残差门槛调小来解决。

本轮用合成方向和现有 Python `north.resolve` 复算【验】：

| 项目 | 结果【验：合成输入，不是现场实验】 |
|---|---|
| 真太阳方向 | 方位 0°、高度 30° |
| 竖直反射面 | 水平法向 `n=(cos15°, 0, sin15°)` |
| 反射目标方向 | 方位 30°、高度 30° |
| 高度角残差 | 0°，通过方案候选的 1.5° 门槛 |
| 融合输入 | 正确 magnetic：yaw=0°、σ=13°；把假目标错误标成有效 solar：yaw=−30°、σ=2° |
| resolver 输出 | `warn`，`conflict=false`，yaw≈330.664°、σ≈1.977°；实际圆周方向误差≈29.336° |

这个反例**不是已实现太阳检测器的实测误报**，而是证明：如果候选生成器仅凭高度残差把目标标为有效，后续融合和黄灯不会自动识别这个错误。NorthResolver 按传入证据工作，不应靠改融合优先级掩盖候选有效性的问题。

建议改成：

> 高度角残差用于排除明显不一致的候选，不能独立确认太阳身份。太阳圆面确认是待验证的方向采集路径；候选身份不明确、疑似反射或证据不足时，记录保持 R0。

实验必须包含与太阳**相同高度角**的反光和人工亮目标，而不只是随手找几个高度不同的灯。形状、饱和区、时序一致性和用户确认可以作为额外线索，但各自仍需验证，不能用“用户点过”代替证据。罗盘预测位置只作搜索提示，不能把搜索范围内选出的结果再当作完全独立的罗盘佐证。

**关闭条件：**删除绝对性结论；登记针对同高度假目标的挑战集、候选有效性规则、拒绝率与误接收率。若单一太阳路径做不到可靠拒绝，先限定经验证的采集条件或增加独立确认，不能只缩小标称 σ。

## V2-02 · P1：走动校准需要划分采集阶段；“同一 AR 会话”不是有效性保证

**位置：v2 §4 第二个理由、§6.1；实验 2 的“闭合差另报”。**

太阳方向在房屋尺度上不依赖站位，这个几何判断可以支持研究“走到可见太阳处确认”。但记录里的 Δ 属于估计的 AR 坐标系；应用会话没有结束，不代表往返移动后该坐标系的偏航误差仍然相同。

当前 `CaptureRecorder.record` 在记录期间逐帧更新原锚点偏移与 `maxDriftM`【验】。如果直接把走出去确认混进 OneTake，需要先说明：哪些是可见域采集帧，哪些只用于方向确认；原始超界记录如何保留，哪些统计用于目标点质量判断。不能为了通过漂移门槛删除走动轨迹，也不能把外面的天空并进室内目标点网格。

**建议首个真实闭环先从原地能确认太阳的目标点开始。** 走动确认可以作为独立实验，不作为首版一定可用的兜底。若接入，应显式区分目标点采集段与校准段，保留各段追踪状态、时间与坐标系连续性；reset、不可证明连续的重定位或追踪中断发生时，不沿用旧 Δ。

“往返闭合差另报”还不够：它需要成为是否允许把该候选应用到原网格的判断依据。实验前定义如何评估、失败如何降级，门槛仍是候选并按项目流程登记。

**关闭条件：**校准帧不会进入原点可见域；原始漂移可追溯；追踪失效时结果降为 R0；成功往返的北向误差有独立真值，不能仅以“回到了原位置”证明 yaw 正确。

## V2-03 · P1：增加检测器接口还不等于五盏灯都有可重算的规则

**位置：v2 §5 `quality.evidence`、阶段 A/C。**

把镜头和水平灯补齐是正确的。但“`DetectHorizonRequest` 与重力的夹角”还不是可实现的完整定义。Apple 的 `HorizonObservation` 提供图像中的角度和仿射变换；需要先把 AR 重力通过相机旋转与图像方向变换到同一个图像坐标系，再比较对应方向，不能直接拿图像角度与三维重力向量相减。[Apple：HorizonObservation](https://developer.apple.com/documentation/vision/horizonobservation)

还需覆盖图像没有可靠地平线、视线接近竖直、窗框或屋檐被识别成地平线的情况。`level` 这盏灯在原规范中是“水平与追踪”；v2 只列地平线夹角，仍缺追踪中断、重力稳定性和运动模糊的聚合规则。

镜头检测也有实际边界：Apple 提醒自然虚化、长曝光或运动模糊可能被当作污迹，建议用稳定拍摄的图像执行检测。扫动关键帧需要先确认满足这个输入条件。[Apple：DetectLensSmudgeRequest](https://developer.apple.com/documentation/vision/detectlenssmudgerequest)

**A 阶段要交付一张规则表，而不是只有字段表：**每项证据的采样对象、单位、图像变换、检测器版本、原始结果、可用性/失败状态、聚合方法，以及 pass/warn/blocked 的候选阈值。反射检查至少区分未运行、不可判定、运行未发现、疑似命中；“运行了且零命中”不能被定义成玻璃必然安全。

关键帧检查结果也不能自动代表所有累积帧。需要说明质量证据覆盖哪些帧、检测失败如何影响累积或整条记录。缺证据时按既有阻断规则处理；若发现这让合理场景几乎都不可用，应回到实验与 ADR 修订，而不是默认 pass。

**关闭条件：**Swift 与 Python 用同一证据 fixture 得出同一灯；缺失、不可判定、单位或坐标错误有明确拒绝/降级路径；灯的等级能从保存的数值和规则版本重算。

## V2-04 · P1：目前“派生状态”和“用户文字”并不是方案说的不同列

**位置：v2 §6.2“只动记录 JSON 与派生的状态文字；笔记……是别的列”。**

当前 `PendingCaptures.commit` 把 Light 状态句写入 `observation.text`；`InspectionObservation.text` 同时被定义为用户文字，并由 `correctText(to:)` 编辑【验】。因此“更新派生状态文字但不碰用户笔记”尚未由当前模型保证。按 v2 原话直接实现，很容易在分析晚到时覆盖用户已改过的说明。

建议保留 `text`/`originalText` 的用户编辑语义，Light 系统状态直接从 SceneRecord 和任务状态派生。旧 Light 状态句的兼容需有迁移规则，不应仅凭文字相似就删除用户内容。不新增 CloudKit 字段可以是优选实现，但不应成为牺牲数据分离的硬限制。

此外，revision/hash 需要避免定义循环：第一次分析之前还没有结果网格，不能只用“包含网格的 inputs_hash”说明怎样阻止旧任务提交。建议区分任务开始时的采集版本/输入清单摘要，与最终结果的分析输入摘要；本地比较与写入在一个串行提交入口完成，先确认数据库提交成功，再清帧卷。

行 UUID 用作任务身份很好，但旧 `PendingCaptures` 仍按 `scene_id` 命名和去重【验】。要关闭撞号问题，恢复、查询、导出与关联路径也必须一起使用可靠身份，不能只改任务文件夹。两个设备各自比较 revision，也不自动构成跨设备的全局互斥；首版可以明确仅采集设备生成该记录的结果，其他设备读取。

**关闭条件：**分析中编辑说明不会丢字；首次无网格任务有明确提交令牌；旧任务不能覆盖新北向；同 scene_id 的不同采集不串行；数据库提交失败仍保留输入；另一台设备晚到的数据不会被描述为已解决的全局并发。

## V2-05 · P2：不做后台调度是合理减法，但 iPad 等待状态必须能解释真实原因

**位置：v2 §3.2、§6.1–6.2。**

支持先采用前台计算、有限收尾、下次启动续跑。原定约二十秒【引：方案估算】尚未是真机性能事实，但无需因此立即增加后台调度系统；应先测再决定。

需要补齐主旅程：用户在手机保存后关闭 App，回家只打开 iPad；iPad 不能仅显示“分析完成后会同步”，让人以为手机一定还在后台工作。它应报告最后已知状态，例如“尚未收到分析结果；请在拍摄设备打开 App 继续”。同步延迟、iCloud 关闭、源设备暂停、源设备不可用，是不同情况；不掌握实时状态就不要声称实时知道它正在分析。

帧卷到期清理也应区分是否已产出有效持久网格：已有网格而删除原帧，不代表不能重算日照；未分析且原帧已删，才是无法完成初次分析。原定十四天【引：v2 候选】建议先作为可调清理策略，同时明确告知到期后果、磁盘占用上限和取消入口。

**关闭条件：**手机退后台、iPad 先打开、源设备多日不启动、已有网格但无原帧等情形都有准确状态；不显示永远无法成功的重试，也不制造“正在处理”的假进度。

## V2-06 · P2：实验要先冻结评价方法；首版范围不要提前等同于 CONDITIONAL

**位置：v2 §2、§4、§7；回应“等 Lee 定”。**

用普通照片做接口冒烟、用 App 帧卷做真实输入评估，这个拆分我支持。Mac 可以承担离线质量比较，但 iPhone 上的延迟、内存、温升与掉帧仍需在目标设备测，不能用 Mac 运行结果填写采集性能。

“至少三个不同有效帧”【引：方案】不自动表示独立证据。不同 frame_id 的相邻帧仍可能重复同一个错误；需要具体的时间/姿态去重规则，并解释它衡量的是重复观测支持，而不是统计独立性。用实验 1 选规则可以，但选择后的同一批样本只能叫开发结果；在独立 holdout 前冻结算法、σ、质量阈值和规则版本。

“晴天且看得见太阳才有时段”是拟议的技术路径限制；它比路线图中的“户外 + 晴天室内”更具体，还取决于太阳是否可见、校准是否可靠，不能直接说两者是同一范围。经过 V2-01 的反例后，更不能把晴天等同于有合格 solar 证据。

建议先写：“初始实验优先覆盖能获得可靠太阳圆面方向证据的场景；产品适用范围由验证结果确定。”报告方向精度时同时报告失败、拒绝、放弃和救场，不能只给成功确认的误差分位数。

## 下一次交付应该是什么

## 本轮证据与验证边界

本轮核对 Git 最新提交、v2、Claude 回应、相关 ADR、质量规范及以下源码：

本轮仅新增反射几何及融合反例复算，未重跑未改变代码的全套测试。未运行真实太阳检测器、Vision 真机实验、走动校准、双设备同步或白卡延时；`field/` 仍无本轮可读取的原始现场数据。API 语义核对使用正文链接的 Apple 官方资料，接口存在不等于该检测器适合当前场景。

**最终建议：支持 v2 的推进方式；优先修正太阳候选有效性、走动校准和文字存储边界，把这些变成 A 阶段的退出条件，然后按证据推进。**
