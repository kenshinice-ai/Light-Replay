# 05 · NorthResolver：真北是多来源一致性问题

版本 0.1 · 2026-09-10

## 1. 问题

ARKit 给的是重力对齐但 yaw 任意的世界坐标。要判断太阳是否落在可见域里，必须知道 AR 世界到真北的旋转 `Δ`（yaw）。没有任何单一来源在室内、阴天、隔玻璃的条件下可靠，所以把它做成融合与冲突检测问题，并把 `σ_Δ` 传播成时段的不确定性。

## 2. 来源

| 来源 | 独立组 | 条件 | 典型 σ（估） | 备注 |

### 2a. 太阳圆面候选的有效性（`sundisk-0.1`，ADR-0021；待实验 2 验证）

做法：镜头对向太阳，在罗盘预测位置附近找过曝亮斑的中心，由该像素的视线方向与此刻的太阳方位得 `Δ = az_true(太阳) − az_ar(视线)`。罗盘的预测只作搜索提示，不算对结果的佐证。

候选被标为有效，必须同时满足（两端校验器拒绝"声称有效但证据不过"的记录）：

| 检查 | 候选阈值【估】 | 拒绝的是什么 |
|---|---|---|
| 高度角残差 `|alt_measured − alt_expected|` | ≤ 1.5° | 高度不对的灯、反光、云边 |
| 太阳高度角 | ≥ 5° | 贴近地平线，折射与遮挡都不可靠 |
| 亮斑处没有深度回波 `depth_m == null` | — | 近处的表面：灯、室内镜面、窗玻璃上的反光（穿过玻璃的真太阳也可能被拒，这是安全的一侧） |
| 亮斑周围一圈是天空 `sky_ring_fraction` | ≥ 0.6 | 嵌在建筑立面里的反光 |
| 买家确认"这是太阳本身，不是反光" | 必须 | 人能看出来而规则看不出的情况 |
| 从扫描到确认追踪连续 `tracking_continuous` | 必须 | 世界坐标动过，Δ 不再是原扫描的 Δ |

**这些是必要条件，不是充分条件。** 竖直反射面保持高度角不变：与太阳同高度、映着天空的玻璃幕墙上的反光，可以通过上面每一条，而方位差几十度；罗盘 σ 13° 时融合器也分辨不出（`3·sqrt(13² + 2²) ≈ 39°`）。fixture 里保留了这个反例（`a_mirror_at_the_suns_altitude_is_not_caught`），它被接受、方向灯是黄灯——这是规则的边界，由实验 2 的挑战集量出它在真实场景里多常见（`07` §5a）。量出来不可接受，就限定采集条件或加独立确认，不靠缩小标称 σ。

走到别处确认：确认段的帧标 `role: calibration`，不进入可见域；追踪中断或重定位后不沿用旧 Δ。第一个真实闭环只用原地能看见太阳的目标点。

## 3. 融合

1. 组内合并：同组多次读数取鲁棒中位（圆周），σ 取组内分散与先验的较大者。
2. 组间融合：加权圆周均值，权重 `1/σ²`。
3. 一致性：任两组的圆周差 `δ_ij = min(d, 360° − d)`，其中 `d = |Δ_i − Δ_j| mod 360`；`δ_ij > 3·sqrt(σ_i² + σ_j²)` 判为冲突。
4. 冲突时不平均：在两两一致的组合中取组数最多者融合；组数相同时，比较组合中最可信的组（顺序 `solar > vps > map > magnetic`）。其余组标"被否决"。
   - 被否决的只有 magnetic：不算冲突，冲突详情照记。
   - 否决了 magnetic 以外的组：算冲突，要求一次最小确认（用户指认墙面或地图拖拽），确认前只出 R0。
   - 一致不等于佐证（ADR-0018）：组合里至少有一对的冲突门槛 `3·sqrt(σ_i² + σ_j²) ≤ 15°`（候选），绿灯才成立；没有这样一对时按只有一组处理（融合 σ ≤ 6° 黄灯，否则红灯并要求确认）。没有佐证的组照常参与融合与冲突检测。
5. 只有一组有效且 σ > 6°：要求一次最小确认，确认前只出 R0。
6. solar 候选进入融合前须通过自身残差检查：窗光斑校准要求光斑边与窗边对应的重投影残差 ≤ 1°（候选），且太阳高度角与光斑几何一致；不通过标 `valid: false`，不参与融合（ADR-0009）。
7. 输出 `Δ`、`σ_Δ`、参与组、被否决组、冲突详情。

**实现定义（northresolver-0.1，`ios/Packages/NorthResolver` 与 `engine/lightreplay/north.py`，由 `engine/tests/fixtures/north-cases.json` 的 219 个用例对齐，容差 1e-9°）。** 上面几步留给实现的地方这样定：

- 组内中位数：先求读数的平均方向，把各读数相对它折到 [−180°, 180°) 再取中位数，避免 0°/360° 把中位数劈开；读数互相抵消、没有平均方向时以第一条读数为参照。只有一条读数时就是它本身。
- 组的 σ：读数自带 σ 的中位数与读数相对中位数的 RMS 分散，取较大者。同一组读数再多 σ 也不缩小（同一传感器的读数不是独立证据）。各来源的先验下限由产生候选的一方加上（罗盘 8°，候选）。
- 没有 σ（σ ≤ 0）或标了 `valid: false` 的候选不参与。
- 融合后的 σ：`sqrt(1 / Σ(1/σ_i²))`。`03` 第 4 节的例子算出 359.78° / 1.77°。
- 组数相同的组合之间：按可信顺序逐个比较成员，先比最可信的，再比次可信的。
- 一致是两两的，不是链式的：A 与 B 一致、B 与 C 一致、A 与 C 冲突时，三者不能同组。

## 4. 定义

- `Δ`：AR 世界 −Z 轴的真方位角（从真北俯视顺时针量到 −Z 轴）。`gravity` 对齐下 −Z 是会话开始时相机朝向的水平投影，所以 Δ 就是开始扫描时相机朝向的真方位角。
- `az_true = (az_ar + Δ) mod 360`；`az_ar` 的定义见 `02-architecture.md` 第 3 节。
- `gravityAndHeading` 对齐下 −Z 即罗盘给出的真北，Δ 应接近 0，差值就是罗盘误差，可作对照。
- 磁偏角由 CoreLocation 处理（`trueHeading`），本模块只处理真北。

## 5. 不确定性传播

SunEngine 对 `Δ ~ N(Δ, σ_Δ)` 采样（候选 64 组），叠加分割边界抖动（候选 ±1°），逐时段统计"直射"比例：≥ 95% 稳定直射；≤ 5% 稳定遮挡；其间为"方向敏感"；太阳穿过未知单元为"资料不足"。用户看到的是时段，不是角度。

## 6. 界面状态

| 状态 | 显示 |
|---|---|
| 没有冲突，且至少一对佐证（`3·sqrt(σ_i² + σ_j²) ≤ 15°`；仅磁罗盘偏离被否决也算） | 绿灯；结果卡写来源与 σ；有被否决的磁读数时注明 |
| 只有一组，或多组一致但没有佐证对；融合 σ ≤ 6° | 黄灯；提示可做一次确认 |
| 只有一组，或多组一致但没有佐证对；融合 σ > 6° | 红灯；要求一次最小确认；确认前只出 R0 |
| 冲突（否决了磁罗盘以外的组） | 红灯；显示分歧，要求确认；确认前只出 R0 |
| 无有效来源 | 只出 R0 |

## 7. Spike 要回答的

- 墙面对齐在 10 个室内点上相对日晷真值的误差分布（中位数、P90）。
- 阴天室内没有轮廓数据时，用户能否 10 秒内完成地图拖拽，误差多少。
- 冲突检测的误报率：晴天同时有 solar 与 map 时，两者差异分布。
- **佐证门槛 15° 是否合适**（ADR-0018）：规则已把"σ 很宽的组与任何组都一致"关在绿灯之外（罗盘 σ 12° 藏得住 17° 的错；一组读数互相矛盾时 σ 到 90°），但 15° 是按"一小时太阳方位"估的。用日晷真值统计：solar / map 两组都在、冲突门槛在 10–20° 之间的场景里，实际方向误差有多大。
