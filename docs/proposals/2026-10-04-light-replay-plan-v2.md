## 1. 交付的定义

**一个目标点、一个日期、一份真实的可见域网格：从现场采集到回家回放可闭环；失败与未知也说得清为什么。**

体验不变：回家点开扫描时那张照片，选日期、拖时间，看这个位置那一刻有没有直射。变的是先后——v1 把还没成立的测量假设直接排了工期；v2 把假设、数据契约和真实验证排在界面前面。

v1 里五处我写错或漏掉的（评审指出，已核对）：

| v1 的说法 | 实际【验】 | v2 |
|---|---|---|
| 只有罗盘 = 方向黄灯，可出"大约"的 R1 | 一组且 σ > 6° 是**阻断**；真机 σ 10–20°，记录里写的就是 `north: blocked` | 罗盘单独永远是 R0；见 §4 |
| R1 看三盏灯 | 校验器要求**五盏都不阻断**；镜头灯现在恒为 blocked，水平灯按写入值 | 镜头、水平两盏要有真检测器与证据，§5 |
| 敏感段宽度 = "±N 分钟" | `SunBands` 按直射比例 ≥ 0.95 / ≤ 0.05 分段，没有事件边界的置信区间 | 不写 ±；直接列三种区间，§3 |
| 帧卷放 Caches，失败可重试 | Caches 会被系统清；清了就无图可分 | 持久目录 + 任务清单，§6 |
| 高度角 > 30° 作天空正种子 | 南纬 37.8° 冬至正午太阳高度约 28.8°（90 − 37.8 − 23.44），走廊里一个种子都没有；而且方向不等于天空 | 种子策略是实验题，§7 实验 1 |

## 2. 分阶段与闸门

每个阶段有"进入下一步的证据"。估时是工作量预算【估】，不是日历承诺；闸门不过就不往下走。

| 阶段 | 做什么 | 进入下一步的证据 | 工作量【估】 |
|---|---|---|---|
| **A · 契约与冒烟** | schema 0.2 与任务状态写成文档 + 两端校验器（§5、§6）；分割冒烟（§7 实验 0）；太阳圆面确认的实验设计与通过线登记（§7 实验 2） | 两端校验器接受 0.1 与 0.2 fixture；冒烟回答"这个 API 给天空点能不能出天空掩膜、失败长什么样" | 3–4 天 |
| **B · 可恢复采集** | Hero 静帧 + 帧卷（同步的图像、姿态、内参、深度、变换链）落持久目录；任务清单；"已保存，可分析"只在输入落稳后出现 | 重启后能定位同一组完整输入；缺输入明确失败；不同分辨率 / 横竖屏下合成场景投到同一方向 | 3 天 |
| **闸门 1** | Lee 用 B 的版本在自家拍评估集（约 20 个帧卷片段），手工描天际线 → §7 实验 1 | 预登记的分割线与"走廊内假天空率"；不达线走 ADR-0010 | 评估 2 天 + Lee 的拍摄 |
| **C · 合成闭环** | VisibilityCore（采样、重投影、计票）；五盏灯的证据与重算；Save 后分析任务与结果提交协议；回放主屏骨架接**标明"合成"**的数据 | 物理夹具、Swift / Python 逐格一致、故障注入（各阶段中断重启）、改北向后旧结果被拒 | 6–8 天 |
| **D · 真实目标点闭环** | 接选定的分割路径与太阳圆面确认；自家一个点从图像到网格到时段全程可追溯；白卡延时对照 | `field/` 采集编号 + 延时事件编号；误差对照 `07` §5 的预登记线（中位 ≤ 10 min、P90 ≤ 20 min【引】），这一步只算集成验证 | 4–5 天 + 一个晴天 |
| **E · 回放体验** | 主屏做完（§3）；天幕"为什么"；Light 卡片入口；然后 Compare 格、其他入口、多日期 | 最大字号 / 横屏 / 深浅色 / 中英文 / VoiceOver 都能选日期、调时间；状态不只靠颜色；数字回归通过 | 5–6 天 |
| **F · 独立验证与交付判断** | 冻结版本；按 `07` W2 / W3 与 `08` 做 holdout（室内外、玻璃、树冠、低太阳） | `07` §5 全部预登记线；false-valid = 0；给 GO / CONDITIONAL / NARROW | 按 `07`，2–3 周现场 |

到 E 结束约 4–5 周工作量【估】，比 v1 的 4 周多：多出来的是 v1 漏掉的镜头 / 水平灯、输入持久化与结果提交协议。两个天气闸门（D 的晴天、F 的现场）决定日历。

## 3. 回放屏（E 阶段做完，C 阶段先出骨架）

### 3.1 主屏

从上到下：

1. **Hero 照片**，叠当天太阳路径与所选时刻的太阳方向标记。标记只表示方向，不描画面里的遮挡物轮廓（方向网格给不出物体轮廓）。太阳不在视野内时在边缘给一个方向提示。照片下一行小字："结果只针对拍摄时手机所在的这个位置"。
2. **日期**：冬季代表日（默认）、春秋分、夏季代表日、今天，加一个**看得见的**日期按钮。显示年份，按场景时区。代码里冬夏用的是固定日期近似，界面写"代表日"，不叫"冬至那一刻"。
3. **时间轴**：日出到日落，手指 1:1 跟手，过状态边界一次轻触感；reduced motion 下只去动画。VoiceOver 下是可调控件（上下滑按 10 分钟走）。
4. **结果区**（只在 R1 画色带）：四种段——稳定直射、敏感（斜纹）、被挡、资料不足（空心）；形状与颜色都不同。
5. **状态句**，全部由工具填数，不写 ±：
   `2027-06-21 · 稳定直射 10:55–13:50 · 敏感 10:30–10:55、13:50–14:15 · 资料不足 15:40 起`
   多段直射分开列，不合并。
6. **证据**（默认折叠）：先说人话——"适用于这个位置；方向由太阳确认；有 6% 的天空隔着玻璃"；展开才是等级、五盏灯、每个查询的覆盖率、算法版本与结果 revision。

最大辅助字号与横屏下允许滚动；不设"一屏放下"的硬条件。

| 状态 | 条件 | 结果区 | 给用户的一句话 |
|---|---|---|---|
| 分析中 / 等待资源 | 采集设备上任务在跑，或分割模型在下载 | 进度，无色带 | 正在分析这次扫描 |
| 在另一台设备上 | 本机没有帧卷，记录仍是 R0 | 无色带 | 分析在拍摄的那台设备上完成后会同步过来 |
| R0 · 方向证据不足 | 方向灯阻断（只有罗盘，或确认失败） | 照片上画**参考**太阳路径（按罗盘，带 ±σ 的宽度），无色带 | 方向只有罗盘，算不出可靠的时段。下次在现场对一下太阳再扫 |
| R0 · 天空资料不足 | 走廊覆盖 < 70%、分割阻断、镜头或水平阻断 | 天幕标出缺的区域，无色带 | 这部分天空没看清（原因），需要重扫 |

"分析完成"不等于"得到有效测量"：分析完成但仍是 R0 是正常结局，原因写明。

### 3.3 天幕与入口

- 天幕（360 × 100 网格展开）作为"为什么这段被挡 / 为什么资料不足"的解释入口，从证据区进。
- 入口第一版只有房产页的 Light 卡片。真实闭环（D）通过后再加照片流角标与 Compare 格。
- Compare 格的写法：`已确认直射 2 h 55（冬季代表日）`；有未知时加"资料不完整"；R0 写原因，不写数字。不叫"日照总时长"。
- 全年热力图不是首个可用回放的前置，放在 E 的后半。

## 4. 方向：保存不设障，R1 要证据

- 扫描结束时如果方向灯阻断，**立刻**提示"现在对一下太阳，回家才有时段可看"，同一屏给"保存为参考"。任何情况下都能保存。
- 第一条确认路径只做**太阳圆面**：把镜头对向太阳，App 在罗盘预测位置附近找过曝亮斑的中心，买家点确认。理由：
  - 自带一道不依赖北向的残差检查：亮斑的高度角（由重力得到）必须等于此刻算出的太阳高度角，差超过门限【估 1.5°，实验 2 定】就拒绝——灯、反光、云边都过不了。
  - 方向确认与站的位置无关：同一个 AR 会话里走到看得见太阳的地方再对，Δ 仍然是这个会话的 Δ。走动引入的偏航漂移要量（实验 2 的一项）。
  - 确认耗时计入 OneTake 时长指标，不单独剔除。
- 太阳确认 + 罗盘：罗盘 σ 13° 时两者"一致"但不构成佐证（ADR-0018），方向灯是**警告**，融合 σ ≈ 2°【验：合成候选】——够出"R1 · 有限制"。绿灯要第二个精确来源。
- 阴天没有太阳：这次扫描停在 R0（参考路径可看）。窗光斑需要已知窗几何与残差检查（`05` §2–3），墙面对齐需要竖直平面 + 建筑轮廓数据 + 选对边；两条各自列依赖后再排期，不作为第一版的兜底。这是第一版明说的限制：**晴天、看得见太阳才有时段**——与路线图汇合门里"CONDITIONAL：限定户外 + 晴天室内"是同一个范围。
- 回家后的按钮写"下次到现场重扫并确认方向"，不暗示离开现场还能补。

## 5. 记录契约（schema 0.2，A 阶段先定）

原则：一行一份记录，记录自带它的证据（ADR-0017）。不新增 CloudKit 字段（Production schema 10-03 刚部署）。

| 内容 | 放哪 | 说明 |
|---|---|---|
| Hero 照片 | Light 观察行已有的 `photoData` / `thumbnailData` / `photoByteCount` | 与普通照片同一套丢字节守卫；分享默认不含 |
| Hero 元数据 | `capture_session.hero_frame` | 原始图像尺寸与内参、编码后尺寸、缩放 / 裁剪 / 旋转变换、界面方向；投影一律经这条变换链 |
| 可见域网格 | 记录 JSON 内联（压缩后 base64），`visibility.states` / `confidence` | 36 000 格，压缩后几十 KB【估】；不再用本机文件路径当引用 |
| 计票 | `visibility.votes` | 分开记"不同有效帧数"与"权重和"；最终态要求的是不同帧数，相关的连拍帧不重复计 |
| 关键帧掩膜 | 记录 JSON 内联，3–5 张 | 只用于抽查与排错。**从网格重算日照可以；从原帧重新分割不可以**（帧卷已删） |
| 分析结果 | `analysis[]` | `query`（带年份的日期、时区、是否代表日）、`segments`（四态）、`totals`（已确认直射 / 敏感 / 资料不足的分钟）、该查询的走廊覆盖、`inputs_hash`、`revision`、各算法版本 |
| 五盏灯的证据 | `quality.evidence` | 新增：镜头（`DetectLensSmudgeRequest` 在 Hero 与关键帧上的结果）、水平（`DetectHorizonRequest` 与重力的夹角）、反射检查（跑没跑、命中几次）。QualityEvaluator 五盏全部按证据重算 |

- 0.1 的记录照旧可读、可校验；Swift 与 Python 校验器、fixture、导出同步升级。
- `inputs_hash` 覆盖：网格与置信度、方向候选与融合结果、地点与时区、查询、影响结果的选项。
- 北向改了：旧 hash 的结果作废，各查询的覆盖率重算（太阳路径在 AR 坐标里移了）。

## 6. 采集与分析任务

### 6.1 帧卷（B）

- 每个分析帧一起存：`frame_id`、ARFrame 时间戳、camera transform、原始尺寸与内参、编码尺寸与变换、曝光、追踪状态、深度图与置信度（及其尺寸、与彩色图的配准约定）。姿态取**同一帧**的，不从 10 Hz 的姿态日志里找邻居。
- 位置：`Application Support/LightSpool/<行 uuid>/`，不进 iCloud、不进备份。任务清单与帧卷同目录。
- 保留期：结果提交成功、用户放弃、或 14 天【估】到期后删除；到期未分析的行标"输入已缺失"。
- 体积【估】：30 秒 × 3–5 fps ≈ 120 帧，JPEG 约 15 MB + 深度约 12 MB，临时占用。
- 无 LiDAR 设备：没有深度项，近场重投影不可用，按 `04` §10 的既有降级。

### 6.2 分析任务（C）

```
Save → 输入落稳（Hero 进行、帧卷 + 清单落盘）→ 报"已保存，可分析"
  → 分割（选定路径）→ 四态 → 落格 → 计票 → 网格
  → 镜头 / 水平 / 反射检查 → 五盏灯按证据重算
  → 时段（标准查询）→ 组装结果 revision n+1
  → 提交：行还在、没被删、行上的 revision 仍是任务开始时的 n、hash 没变 → 写入；否则丢弃这次结果
  → 清帧卷（留关键帧掩膜在记录里）
```

- 执行：Save 后在前台跑，行上有进度；退到后台用系统给的短暂宽限把当前阶段做完；没做完的下次启动从清单续。每个阶段可重入。**第一版不引入后台调度**（`BGProcessingTask` 不是无缝接力；`BGContinuedProcessingTask` 以后再评估）——20 秒量级的任务不值得那套机制。
- 提交只动记录 JSON 与派生的状态文字；笔记、房间、标签是别的列，不碰。任务提交前查行是否存在，删除优先。
- 任务身份 = 行 uuid + `scene_id`（跨设备同日 `scene_id` 撞号是 HANDOFF 已知未结项，在这里一并处理）。
- 状态：等待分析、分析中、等待资源、可重试失败、输入已缺失、完成（R0，附原因）、完成（R1）。只有输入还在才给"重试"。

## 7. 三个实验（先于主链）

| 实验 | 回答什么 | 怎么做 | 通过线 |
|---|---|---|---|
| **0 · 分割冒烟**（A） | `GenerateIterativeSegmentationRequest` 给一个天空里的点，出来的是不是天空；失败长什么样；每帧多久 | Mac 上的小命令行（这个请求在 macOS 27 也有【验：SDK 接口】），用 Lee 随手拍的 5–10 张带天空的照片 | 不设线，只为决定实验 1 比哪几条路 |
| **1 · 分割评估**（闸门 1） | 哪条分割路径能用 | 输入是 B 版本拍的帧卷片段（带重力、深度、内参）+ 手工天际线。对比：(a) Vision 迭代分割，包含点由"地平线以上 + 无近深度 + 亮且平滑"共同挑出，排除点取 LiDAR 近物（接口有 `addIncludedPoint` / `addExcludedPoint`，结果可为空【验】）；(b) 不用 Vision 的启发式基线；(c) 手工 | 预登记：IoU ≥ 0.90【引 `07` §5】；另报走廊内"遮挡判成天空"的比例、无天空帧（天花板占满）必须零天空证据、无种子不崩溃、每帧延迟。整体 IoU 好看但走廊错的样本单列。评估帧不再用于最终验收 |
| **2 · 太阳圆面确认**（A 设计，D 前完成） | 点一次太阳能把 Δ 定到多准；残差检查拦不拦得住假目标；走出去再走回来偏航漂多少 | DEBUG 版里的确认步骤；自家晴天多次；真值按 `08` 的日晷协议；对灯、对玻璃反光各试几次 | **测之前登记**：Δ 误差中位 ≤ 2°、P90 ≤ 4°【估，待 Lee 认可后写进 `07` §5】；假目标全部被残差拒绝；走动往返的闭合差另报 |

三票【引 v1】改为"至少 3 个不同有效帧"【估】，由实验 1 的数据校准。

## 8. 验收分三层（不互相顶替）

1. **合成闭环**（C）：实现遵守契约——物理夹具、两种语言一致、故障注入。
2. **自家现场**（D）：真实输入走得通——一个点、一天延时，带采集编号与延时事件编号。这是集成验证，不是测量链的验收。
3. **独立 holdout**（F）：冻结版本后按 `07` W2 / W3：误差中位 ≤ 10 min、P90 ≤ 20 min、false-valid = 0【引】。通过线测前登记，不事后改；失败、放弃、未知、人工救场都进报告。

## 9. 认可后先写的 ADR（按项目约定：ADR → 蓝图 → 规范）

- **ADR-0021** 方向确认：保存不设障；R1 需要罗盘以外的方向证据；第一条路径是太阳圆面及其残差检查；阴天停在 R0。
- **ADR-0022** schema 0.2：资产内联进记录、Hero 复用照片列、分析结果的 revision 与 `inputs_hash`、五盏灯的证据字段。
- **ADR-0019 补记**：帧卷在分析完成前是不可重建的本地输入（持久目录、保留期）；"复算"指从网格重算日照，不指重新分割。

## 10. 六问（`14` §8）
