# 04 · 采集协议：OneTake、视点锁定、太阳走廊、玻璃

版本 0.1 · 2026-09-10

## 1. 一句话

**在你要坐的位置，对着窗或天空，一次采集。** 目标点 = 镜头所在的点 + 用户确认的高度；扫描过程中镜头尽量留在这个点附近，偏离的部分由深度修正或降权。

## 2. 三个动作

| 动作 | 目的 | 产出 | 预算 |
|---|---|---|---|
| 锚定并拍（Hero） | 得到"这是我站的地方"的照片与锚点 | Hero frame、锚点、时刻、位置 | 5 s |
| 原位扫天 | 得到这个点能看见的天空 | 四态可见域、走廊覆盖率 | 15–30 s |
| 方向确认（自动为主） | 让 AR 坐标挂到真北 | 方向候选（磁、墙面、太阳/光斑、VPS） | 0–10 s |

## 3. 太阳走廊

- 由用户的问题决定：冬季早餐 = 6 月 ± 6 周、7:00–10:00；全年 = 全部日期、日出到日落；下午西晒 = 11 月–次年 3 月、14:00–日落（候选【估】）；自定义 = 用户给定的日期范围与时段。
- 走廊 = 该时段内太阳出现的 (方位, 高度) 集合，外扩 3°（方向 σ 与分割边界的余量）。
- 覆盖率只按走廊内的单元计算；界面用环形指示缺口，只提示"会改变答案"的方向。
- 参考数据（平地、忽略折射）：墨尔本冬季日出约 60°、日落约 300°，夏季约 120° / 240°；正午高度冬至 28.8°、夏至 75.6°。悉尼 32.7° / 79.5°。走廊由 SunEngine 实时算，不用口诀。

## 4. 视点锁定与漂移

| 情况 | 处理 |
|---|---|
| 像素有 LiDAR 深度且 `z < D_near`（候选 4 m） | 重投影到目标点（`02-architecture.md` 第 3 节） |
| 像素无深度或 `z ≥ D_near` | 直接用相机方向；记录漂移 `d` 与角误差上界 `atan(d / D_near)` |
| 漂移超过 `tolerance_m`（候选 0.15 m，非 LiDAR 0.10 m） | 帧降权；界面提示"回到圆圈" |
| 漂移超过 `drift_limit_m`（候选 0.40 m；SceneRecord 里的 `max_drift_m` 是观测到的最大值，不是这个阈值） | 帧不并入；若持续，建议重扫 |

阈值全部是候选，spike 分别测 0.10 / 0.15 / 0.25 m 对近窗框与远遮挡的影响后再定。

实时覆盖与这张表同一把尺（2026-10-05）：0.40 m 以内的帧算"看过"，超过 0.15 m 时界面仍提示回到圆圈。此前实时覆盖与帧卷都按 0.15 m 截断，看全年太阳时抬头的帧有一半不算数也没留下（`spike/2026-10-05-scan-coverage.md` §2c）。帧卷另外多留到 0.50 m，给定上限的实验用；留下不等于使用。

## 5. 玻璃与曝光

- 隔玻璃扫描是常态。分割输出四态，**反射可疑的像素记为"玻璃不确定"**，不记为天空。
- 曝光：扫描时锁定较低曝光（以天空不过曝为准），Hero frame 单独曝光。
- 识别信号：室内灯具、家具的镜像；亮度异常一致的"天空"；深度指示在玻璃面附近。关键帧另用端侧 FM 图像理解给出"有反射 / 窗帘未拉开 / 天空过曝"的帧级标记，只作辅助信号（ADR-0010）。
- 首次采集前预下载分割模型资源；未下载时手工涂抹。
- 能开窗时提示开窗；**不建议"到阳台扫"作为修复**，那是另一个视点。

## 6. 质量门槛（五盏灯）

| 灯 | 通过 | 警告 | 阻断 |
|---|---|---|---|
| 水平与追踪 | 追踪正常，重力稳定；`DetectHorizonRequest` 的地平线与重力方向一致 | 短暂 limited | 长时间 limited、运动模糊 |
| 镜头 | `DetectLensSmudgeRequest` 未检出脏污 | 轻度脏污，提示擦拭 | 明显脏污，提示擦拭后重扫 |
| 走廊覆盖（`coverage_pct`，定义见 `03-scene-record.md` 第 5 节） | ≥ 90%（候选） | 70–90% | < 70% |
| 方向 | 没有冲突，且至少一对佐证：一致且 `3·sqrt(σ_i² + σ_j²) ≤ 15°`（ADR-0018；仅磁罗盘偏离被否决也算） | 只有一组，或多组一致但没有佐证对，融合 σ ≤ 6° | 冲突（否决了磁罗盘以外的组）；没有佐证对且融合 σ > 6°；无有效来源 |
| 分割 | 玻璃不确定 < 10% 走廊 | 10–25% | > 25% 或反射未识别 |

任一阻断只出 R0。五盏灯的状态与降级原因都写入 `quality`。

**谁来判（quality-0.1）。** 灯是结论，不是输入：QualityEvaluator 按记录里的证据重算，校验器拒绝写入值与证据不符的记录，说高了说低了都拒绝（`ios/Packages/SceneRecord` 的 `QualityEvaluator`，Python 对照 `engine/lightreplay/quality.py`，共用 `engine/tests/fixtures/quality-cases.json` 的 29 个用例）。

| 灯 | 用什么证据重算 | 边界 |
|---|---|---|
| 走廊覆盖 | `visibility.coverage` 的单元计数 | 用整数比较，不做除法：63 / 90 恰好是 70%，算警告；没有走廊证据算阻断 |
| 方向 | `north.candidates` 经 NorthResolver 融合（`05` 第 3 节） | 无有效来源算阻断 |
| 分割 | `glass_cells / corridor_cells`，以及有没有分割来源 | 恰好 10% 与恰好 25% 都算警告；没有分割来源算阻断。**"反射未识别"在 schema 0.1.0 里没有可重算的证据，尚未判** |
| 水平与追踪、镜头 | schema 0.1.0 不带检测器的证据，按写入值 | 只查能查的部分：并入可见域的帧必须追踪正常，且离锚点不超过漂移上限（第 4 节，候选 0.40 m） |

证据不足一律是阻断，不是默认通过。

**quality-0.2（schema 0.2.0，ADR-0022）：五盏都按证据重算。** 两端共用 `scene-v2-cases.json`；阈值全部是候选【估】，独立 holdout 之前冻结，之后不放宽。

| 灯 | 证据（采样对象，单位） | 通过 | 警告 | 阻断 |
|---|---|---|---|---|
| 水平与追踪 · 追踪 | 扫描帧（`role: visibility`）的 `tracking_state` 与 `t`；追踪首次正常之后，最长一段不正常的持续时间（秒）。记录保留每次状态变化帧（ADR-0020），所以一段从它的第一帧算到下一个正常帧 | ≤ 0.5 s | ≤ 2.0 s | > 2.0 s；出现 `limited:relocalizing`（世界坐标可能动了）；从未正常 |
| 水平与追踪 · 地平线 | `quality.evidence.horizon`：`DetectHorizonRequest` 在一张稳定帧上的结果。先把 AR 重力经相机旋转与图像方向投到同一图像坐标，再与检测到的地平线角度相减，得 `residual_deg`（度） | `measured` 且 ≤ 2°；或 `not_found`（画面里没有地平线，室内多数如此，不扣分） | `measured` 且 ≤ 5° | `measured` 且 > 5°；`not_run` |
| 镜头 | `quality.evidence.lens`：`DetectLensSmudgeRequest` 在锚定时的稳定帧（Hero）上的 `confidence`（0–1）。扫动中的帧有运动模糊，会被当成污迹，不用 | `measured` 且 < 0.3 | `measured` 且 < 0.6 | `measured` 且 ≥ 0.6；`unusable_input`（没有够稳的帧）；`not_run` |
| 走廊覆盖 | 同 quality-0.1 | ≥ 90% | ≥ 70% | 其余 |
| 方向 | 同 quality-0.1（NorthResolver） | | | |
| 分割 | 玻璃占比同 quality-0.1，再叠加 `quality.evidence.reflection.status` | `none_found`：按玻璃占比（**不等于没有玻璃**） | `undetermined`、`suspected`：至少警告 | `not_run`（"反射未识别"） |

水平与追踪取两项里较差的一项。运动模糊不设单独的判据：由帧卷的入选规则挡在累积之前（§12）。检查结果覆盖哪些帧写在各自的 `frame_id` / `frames_checked`；关键帧上的结论不自动代表所有累积帧。若这些规则让合理的场景几乎都不可用，回到实验与 ADR 修订，不默认通过。

## 7. 方向确认（详见 05）

- 自动：磁罗盘始终记录；墙面对齐在检测到竖直平面且有轮廓数据时自动出候选，用户只需点"我面对的是这面墙"；VPS 在户外可用时自动。
- 晴天：若地面有窗光斑或画面里有太阳，提示点一下作校准。
- 阴天室内：靠墙面对齐；没有轮廓数据时让用户在地图上把墙拖到对齐，标"手工"。

## 8. 用户指引（写进界面）

| 指引 | 原因 |
|---|---|
| 站在你会生活的位置，手机放到那个高度 | 结果是这个点的 |
| 转动手机，不要转动身体；让绿点留在圆圈里 | 减少镜头漂移 |
| 画面里有窗就对着窗，窗框会自动算作遮挡 | 不需要先量窗 |
| 天空太亮时按提示降低曝光 | 分割依赖天空不过曝 |
| 有太阳或地上有光斑，点一下 | 最便宜的方向校准 |
| 离钢柱、冰箱、汽车 1 米以上 | 磁干扰 |
| 能开窗就开窗；不能开也可以扫，App 会标注 | 反射 |
| 告诉中介一句："我拍窗外的天空测光线" | 礼貌与边界 |

## 9. 边界

- 只拍目标点、窗与天空；不拍人、物品、文件；不录音。授权清单见 `field/templates/consent-checklist.md`。
- Hero frame 可能含房间局部：默认本机保存，分享默认不含。
- 法律边界见 `11-compliance-boundaries.md`；"只拍天空"是行为规范，不是法律豁免。

## 10. 非 LiDAR 与导入

- 非 LiDAR：R1 可用，漂移按阈值；R2 不可用。
- 导入照片：只进 R0。

## 11. Light scan 界面（2026-10-01 实现）

入口：Inspect 底栏右侧 **Light**；房产详情的 Light 区块 "Scan the light here"。全屏呈现（`fullScreenCover`），Inspect 的相机先停，ARKit 独占相机。

| 部分 | 做什么 | 实现 |
|---|---|---|
| 相机 | RealityKit `ARView` 显示采集器自己的 ARSession，记录与画面是同一个会话 | `ARCameraView`，关闭运动模糊、HDR、景深等渲染效果 |
| 两段式 | 打开即预览（追踪、罗盘、定位预热）；按 **Start** 才开始记录，锚点在下一帧正常追踪时锁定 | `CaptureRecorder.startPreview()` / `start()` |
| 太阳路径 | 冬至（主）、春分、夏至三条弧，10 分钟一点，每 3 小时标时刻；弧上写明是哪一天，文字按实测宽度折行并留在屏幕内，字号与相机上的控件一样在 accessibility2 封顶，不画在顶部控件下面（"Shortest day · 21 Jun"、"Equinoxes · Mar & Sep"、"Longest day · 21 Dec"——只写 "20 Mar" 会被读成 App 以为的今天，Lee 2026-10-05）；当前太阳位置标 "Now"。看过的段变太阳黄，没看过的段为白色虚线 | `SunPathOverlay`（Canvas），弧线由 SunEngine 算，`az_ar = az_true − Δ` |
| 方向 Δ | 罗盘实时估计：`Δ = trueHeading − az_ar(相机)`，取按下 Start 之后到此刻全部可用读数的圆周中位数：与记录里罗盘候选同一个合并（`05` §3）、同一个起点（预览期的读数在 Start 时清掉，记录的读数表也从那里开始），每条读数计一次、不抽稀，σ = max(报告精度, 读数分散)；相机俯仰超过 30° 的读数不用（`05` §2）。不用最近若干条的滑动窗口：那样路径会跟着罗盘在屏幕上滑（2026-10-05 单次扫描内 27–204°【验】）。罗盘不设航向过滤（`headingFilter` 默认 1°，手机端平不动时一条读数都没有），读数按 10 Hz 取样（ADR-0020 补记）。罗盘的参考边随界面方向更新（`headingOrientation`；iPhone 可横屏，2026-10-03），每条读数记下当时的设备方向。右上角显示 "Compass ±σ°"，结果卡写 "approximate" | `LiveYaw`；NorthResolver 融合仍按 docs/05 离线做 |
| 问题 | Winter sun（默认，冬至 ± 6 周，按半球取 6 月或 12 月）/ All-year sun；可在扫描中切换，已看过的部分保留；切换后覆盖率与达标状态按新问题重算，重算期间不显示达标 | `LightQuestion` |
| 覆盖 | 相机视锥看过的天空格（去掉每边 8% 边缘），只在正常追踪、视点漂移 ≤ 漂移上限（0.40 m，§4）、转速 ≤ 60°/s 时计入；覆盖率 = 走廊内看过的格 / 走廊格。目标 90%（候选，与第 6 节走廊灯一致） | `SkySweep`、`CorridorProgress` |
| 指引 | 每次一句，优先级：追踪 → 锚定 → 回到圆圈 → 慢一点 → 定位 → 太阳路径就绪 → 找北（"把手机端平，对着前方停一下"：镜头朝天时没有可用的罗盘读数）→ 已覆盖 → 朝缺口转（左右 / 上下，指向最近的未看走廊格）。达标句是 "Sun path covered. Tap Save."：说的是镜头覆盖，不是天空或日照 | `ScanCoach` |
| 视点 | 中央圆圈；绿点是镜头相对起点的水平位置，按容差缩放，超出变橙 | `driftDot` |
| 保存 | 达标后 Save 变为主按钮并有成功触感；未达标点 Save 先询问；关闭时询问是否丢弃。保存走 PendingCapture → 行（R02）。结果是系统面板，分两块："Scan saved"（镜头覆盖了问题路径的百分之几、方向、地点）与 "Sunlight not calculated yet"（当前分不清天空与建筑，没有小时数；分析就绪后这个点可能需要重扫）。保存失败时保留这次扫描，可以重存，不必重扫 | `LightCaptureSaver`、`LightResultSheet` |
| 图例 | 准备阶段显示：实线 = 镜头看过，虚线 = 还没有（形状与颜色都不同） | `LightScanView.legend` |
| 触感 | 锚点锁定（轻）、达标（成功）、保存成功 / 失败 | `.sensoryFeedback` |
| 大字号 | 相机上的悬浮控件在 accessibility2 封顶；顶栏放不下时问题选择独占一行；进度数字移到圆环旁；结果面板完全跟随字号、可滚动 | `ViewThatFits` |

保存后的计算（ADR-0019）：Save 先写 R0 记录；天空分割与可见域累积在之后批量跑，完成后更新同一条记录；失败时记录仍是 R0。扫描中只做"看过哪里"的引导。

诚实边界：**"看过"不等于"是天空"**。当前没有天空分割，所以不判断直射、不出小时数，记录仍是 R0；结果卡明说"日照时段要等天空分析"。五盏灯里只有走廊覆盖有了前身（"看过"的覆盖），镜头脏污、分割、方向两组一致、曝光锁定都还没接。

模拟器（仅 DEBUG）：ARKit 不可用时用脚本化的假相机扫过北半天空，Δ = 0，画面是画出来的天空与地面，标注 "Simulator · pretend camera"。它只用于看界面和 UI 测试（`LightScanUITests`），真机永远不会走这条路。


## 12. 帧卷与分析任务的契约（ADR-0019 补记、ADR-0022；阶段 B / C 实现）

**帧卷（现场的帧离开现场就拿不回来，分析完成前它是要保住的输入）**

- 入选：追踪正常、离视点 ≤ 0.50 m、转速 ≤ 60°/s 的帧，3–5 fps【估】（真机 1.7–3.3 fps【验】，`PR-20261005-01…09`）。每帧记下自己离视点的距离；0.15 m 以外的怎么降权、0.40 m 以外的不并入，是分析任务按 §4 做的事，帧卷只负责不丢。相邻入选帧要么相隔 ≥ 0.3 s、要么视线方向相差 ≥ 5°【估】——这是"重复观测支持"的去重，不是统计独立；`votes.min_distinct_frames` 数的就是这样的帧。
- 每帧一起存（同一帧的，不从 10 Hz 的姿态日志里找邻居）：`frame_id`、ARFrame 时间戳、camera transform、原始图像尺寸与内参、编码后尺寸与缩放 / 裁剪 / 旋转、曝光、追踪状态、深度图与置信度及其尺寸和与彩色图的配准约定、`role`。
- 坐标链写死一条：AR 原生图像（横向、左上原点、像素）→ 编码图像 → 掩膜；Vision 的归一化坐标原点在左下，换算只在适配器里做一次。
- 位置：`Application Support/LightSpool/<行 uuid>/`，不进 iCloud、不进备份；清单文件与帧同目录。
- "已保存，可分析"只在 Hero 进了行、帧卷与清单都落盘之后出现。
- 清理：结果提交成功后删；买家放弃这次扫描时删；到期（14 天【估】，可调）删并告知。已有网格而原帧已删：日照仍可重算。未分析而原帧已删：标"输入已缺失"，不再给重试。有磁盘占用上限与取消入口。
- 无 LiDAR 的设备没有深度项，按 §10 的既有降级。

**分析任务**

- 前台执行，行上有进度；退到后台用系统给的短暂宽限做完当前阶段；没做完的下次启动从清单续。每个阶段可重入。第一版不引入后台调度。
- 提交令牌与串行提交入口见 ADR-0022 第 4 条。数据库保存成功之后才清帧卷。删除优先：提交前查行是否还在。
- 只有采集设备生成结果。另一台设备不知道采集设备此刻在做什么，只说它知道的：没收到结果时写"还没有收到分析结果，请在拍摄的那台设备上打开 App"，不写"正在分析"。iCloud 关闭、同步延迟、源设备多日未开，是不同的状态，各说各的。
- 状态：等待分析、分析中、等待资源（模型下载）、可重试失败、输入已缺失、完成（R0，附原因）、完成（R1）。"分析完成"不等于"得到有效测量"。

**阶段 B 的恢复验收清单**

1. 输入落盘中途杀进程 → 重启后这次扫描要么完整可分析，要么明确标为不完整并保留 R0 记录；不出现"已保存，可分析"而输入缺一半。
2. 分析中途杀进程 → 重启后从清单续，不重复提交，不丢输入。
3. 结果提交时数据库保存失败 → 帧卷仍在，可重试。
4. 提交成功后、清理前杀进程 → 重启后只清理，不再分析。
